# 思い出跡地

> 思い出を地図に残し、友達の思い出を街で拾う。

## このREADMEの目的

このファイルは、実装を担当するCodexがプロダクトの意図とMVPの境界を理解し、仕様を勝手に膨らませずに開発を進めるための基準書である。

実装上の判断で迷った場合は、機能の多さよりも次の体験を優先すること。

> 自分の思い出はいつでも、グループの思い出は所属中かつグループが存続する間、場所を問わず振り返れる。友達の思い出は、その場所に近づいたときに発見し、コレクションに残る。

## 開発コマンド

- `npm install` — ロックファイルに従って依存関係をインストールする。
- `npm run start` — Expo開発サーバーを起動する。
- `npm run start:go` — Expo Go用に開発サーバーを起動する（地図は開発ビルドの案内のみ）。
- `npm run start:dev` — インストール済みの専用開発ビルドへ接続する。
- `npm run build:ios` — XcodeでiOS専用開発ビルドを生成し、起動する。
- `npm run build:android` — Android SDKでAndroid専用開発ビルドを生成し、起動する。
- `npm run lint` — Expo・React Native・TypeScript向けのLintを実行する。
- `npm run format:check` — Prettierのフォーマット規約への適合を確認する。
- `npm run typecheck` — ファイルを生成せずにTypeScriptの型を検査する。

### Google Mapsの開発ビルド

Issue34で基本地図の表示・パン・ズームを導入し、Issue35で本人投稿と選択したグループの投稿マーカーを接続する。東京駅周辺の公開の固定地点から表示し、現在地・位置権限・移動履歴は取得しない。iOS・AndroidともGoogle Mapsを指定し、Apple Mapsへ切り替えて問題を回避しない。

Expo Goは共通のネイティブアプリであり、このプロジェクト専用のキーやネイティブ設定の検証には使わない。地図タブは案内だけを表示し、ほかのタブは利用できる。Webでもネイティブ地図を生成しない。専用開発ビルドはこのアプリ用のネイティブ機能・設定を組み込んだテスト用アプリである。

#### キーの制限と料金の境界

- Google Cloudプロジェクトへ有効な請求先を紐付け、Maps SDK for iOS／Maps SDK for Androidを有効化する。
- iOSキーはiOSアプリ制限を付け、bundle identifierを`com.k2kitano02.omoideatochi`にする。API制限はMaps SDK for iOSだけにする。
- AndroidキーはAndroidアプリ制限を付け、packageを`com.k2kitano02.omoideatochi`にする。使用するビルドの署名証明書SHA-1を登録し、API制限はMaps SDK for Androidだけにする。開発用署名と配布用署名は別なので、公開時には再確認する。
- キーはOS別に分け、制限なしキーで動作確認しない。キーはアプリから取り出され得る。`.env`はGitへの誤公開を防ぐ手段であり、配布後の秘密保持手段ではない。
- Map IDを設定しない。2026-10-10確認時点で、Map IDなしのMaps SDK基本地図は回数無制限の無料対象だが、請求先の有効化は必要。Street View・Places・住所変換・経路検索・Maps JavaScript APIは使わない。Map IDや別APIの追加まで無料と保証しない。
- アプリ制限・API制限だけで悪用を完全に防げるとは扱わない。Google Cloudの利用状況を確認し、意図しない利用時はキーを停止・交換し、再ビルドする。予算通知は課金を自動停止する上限ではない。
- 将来有料APIを追加する場合は、別キー・サーバー経由・料金対策を別Issueで検討する。このキーの許可APIを安易に拡張しない。MapsキーでSupabase投稿の閲覧権限を与えず、既存認証・RLSは別に維持する。

参照: [Googleのキー保護方針](https://developers.google.com/maps/api-security-best-practices)、[Maps SDKの課金対象](https://developers.google.com/maps/billing-and-pricing/sku-details#maps-sdk)、[料金表](https://developers.google.com/maps/billing-and-pricing/pricing)、[iOSの請求先要件](https://developers.google.com/maps/documentation/ios-sdk/usage-and-billing)。料金やSDK条件は導入・公開時にも確認する。

#### ローカル設定と起動

1. Node.js 22.18以上を使用する。`app.config.ts`が参照するTypeScript設定ファイルをNodeの型除去機能で読み込むため必要である。依存は`npm install`で導入する。
2. Git管理外の`.env`へ、`.env.example`にある`GOOGLE_MAPS_IOS_API_KEY`と`GOOGLE_MAPS_ANDROID_API_KEY`を設定する。既存のSupabase設定は残す。片方だけ設定した場合、未設定OSでは地図キー設定の案内を表示する。キー全文をチャット・Issue・PR・ログへ貼らない。
3. iOSはXcodeの初回設定・CocoaPodsを準備する。生成済みの`ios/`がある場合は、キー設定後に手動変更・署名設定を退避し、`npx expo prebuild --platform ios --no-install`でネイティブ設定へ反映する。シミュレーターでは`npm run build:ios`、接続したiPhoneを選ぶ場合は`npm run build:ios -- --device`を使う。実機の開発者モード・信頼設定・Appleアカウントによる署名は利用者が確認する。ローカル実機確認のためだけに有料Apple会員へ自動加入しない。
4. AndroidはJDK 17、Android Studio、Android SDKのplatform／build-tools／platform-tools／command-line tools／emulatorを準備する。規約への同意は利用者が行う。ビルドが要求するSDKバージョンを揃え、実機またはGoogle Play対応のARM64仮想端末を用意する。`JAVA_HOME`、`ANDROID_HOME`とSDKへのPATHは自分の配置に合わせ、既存シェル設定を上書きしない。
5. Androidの署名確認用に`npx expo prebuild --platform android --no-install`で生成し、`cd android`の後に`./gradlew signingReport`で開発ビルドのSHA-1をローカルで確認する。署名の秘密鍵を公開しない。CloudへpackageとSHA-1を登録したAndroidキーを`.env`に入力する。手動変更・署名設定を退避したうえで、リポジトリ直下から再度`npx expo prebuild --platform android --no-install`を実行してキーをネイティブ設定へ反映し、`npm run build:android`を実行する。
6. ビルド済みアプリのJSだけを更新する際は`npm run start:dev`を使用する。停止にはターミナルでCtrl+Cを使う。起動した仮想端末も確認後に終了する。

生成される`ios/`・`android/`、実キーの`.env`、署名秘密鍵はGit管理外である。キーはビルド時にnative pluginへ渡し、独自の`extra.googleMaps`には各OSの設定済みフラグだけを入れる。`EXPO_PUBLIC_`のMapsキーは追加しない。設定・ビルドログはキーを含む可能性があるため、そのまま共有しない。

キー、アプリ識別子、config plugin、ネイティブ依存を変更した場合は、対象OSのprebuildでネイティブ設定を同期してから再ビルドする。`ios/`・`android/`が既にあると`expo run:*`は通常prebuildを省略するため、ビルドだけでは設定変更が反映されない。手動変更や署名設定を事前に退避し、無条件の`--clean`で削除しない。prebuildが`package.json`の起動scriptを変更した場合は差分を確認し、既存の`ios`・`android`と専用の`build:*`の役割を保つ。開発サーバーの再起動やJS更新だけではインストール済みアプリのキーは更新されない。設定済みフラグも、ネイティブ機能やキーが最新のビルドへ反映されたことを保証しない。

Xcode 27／iOS 27では画面の起動にUIScene方式が必要なため、Expo 57.0.23以降と`expo-build-properties`の`ios.enableSceneSupport: true`を使用する。SDK 58への更新は行わない。古い生成済み`ios/`がある場合は、手動変更や署名設定を退避してからiOSだけを再生成し、再ビルドする。Androidの署名ファイルを巻き込まない。[Expo公式のSDK 57対応手順](https://github.com/expo/fyi/blob/main/ios-scene-lifecycle.md#staying-on-sdk-57-with-xcode-27)を参照する。

Android Studioの同梱Javaと、ターミナルの`JAVA_HOME`は別に選択される場合がある。今回の環境ではターミナルのJDK 17でビルドが成功した一方、Android StudioのJDK 25ではCMake／Prefabの同期に失敗した。このプロジェクトのGradle実行用Javaを17に揃えて解消した。生成済みの`android/gradle/gradle-daemon-jvm.properties`がある場合、その`toolchainVersion`も確認する。この指定は`JAVA_HOME`より優先されるため、Mac全体のJava設定を変えるだけでは解消しない。[GradleのDaemon JVM設定](https://docs.gradle.org/current/userguide/gradle_daemon.html#sec:daemon_jvm_criteria)を参照する。

#### 地図が出ない場合と検証範囲

- キー未設定／Expo Go／Webは画面の案内に従う。古い専用ビルドでネイティブ機能が不足する場合は再ビルドする。JSだけで任意のネイティブ障害を防げるとは保証しない。
- 準備完了まで15秒以上かかる場合は案内を表示する。「地図を再読み込み」で地図を作り直せる。タブを離れると地図と待機タイマーを破棄する。地図タブへ戻ると東京駅周辺の初期位置・倍率へ戻る。表示位置・倍率の保持は今回の対象外である。
- `onMapReady`はSDKの準備完了であり、Googleのキー認証やタイル表示成功の証明ではない。空の地図でも通知される場合がある。読み込み表示が消えても、実際のタイルを目で確認する。
- 空の地図は通信、請求先、SDK有効化、OS別のキー制限、iOS識別子／Android package・署名SHA-1と、キー変更後の再ビルドを確認する。Xcode／Android Studioのネイティブログも確認するが、キー・認証情報は共有前に伏せる。原因を推測してAPI制限を外さない。
- 各OSの専用開発ビルドでタイル・パン／ズーム・Google帰属表示・タブ移動と復帰・ログアウトを確認する。案内や再試行ボタンは地図外に配置し、帰属表示を覆わない。

Jestのnative SDK代替を使ったテストは、設定判定・描画引数・待機／再試行・タブ切替の回帰を検証するもので、地図タイルの実表示は証明しない。Issue34ではiOS 27シミュレーターの開発ビルドでタイル表示・パン／ズーム・タブ復帰・再読み込みを確認済み。AndroidのGoogle Play対応ARM64仮想端末でも利用者が地図表示と操作を確認し、両OSでの確認完了を報告した。iPhone・Androidの物理実機での確認は未実施であり、仮想端末の結果で実機確認を代替したとは扱わない。OSごとの実施範囲をIssue／PRに記録する。

参照: [Expoの地図設定](https://docs.expo.dev/versions/latest/sdk/map-view/)、[ローカル開発ビルド](https://docs.expo.dev/guides/local-app-development/)、[Android環境の準備](https://docs.expo.dev/workflow/android-studio-emulator/)。

#### 投稿マーカーの表示（Issue35）

- 初期状態は自分の個人投稿だけを表示する。所属グループをチェックすると、そのグループの投稿を追加する。自分の投稿は金色の丸、グループは`G1`などの番号で区別する。
- 縮小時は画面上で近いマーカーをまとめて件数を表示し、拡大時は個別表示する。まとまったマーカーを押すと拡大する。本人投稿とグループ投稿、異なるグループ同士を混ぜず、DBの投稿や座標を統合・変更しない。
- RPCで許可された投稿位置だけを取得する。未発見のフレンド投稿・写真・投稿者名・メモ本文は地図へ渡さない。投稿詳細・撮影・現在地取得・発見通知は対象外である。
- 投稿はページ単位で取得し、「投稿の続きを読み込む」で追加する。表示件数とクラスタは読み込み済みの投稿だけが対象であり、全保存件数ではない。
- チェック変更・再取得では旧投稿を消してから取得し、遅れて届く旧応答は破棄する。続きの通信失敗では取得済み投稿を保持して再試行できるが、権限拒否では投稿を消す。
- 「投稿を再取得」とタブ復帰で所属グループを確認し直し、退出・解散済みのグループは選択から除く。選択は同じログイン中のタブ移動では保持するが、アカウント変更時にリセットする。地図の位置・倍率は従来どおりタブ復帰時に初期位置へ戻る。
- 権限変更の常時監視は行わない。別端末での退出・解散・削除は次の取得に反映され、端末へ既に送信した情報の回収を保証しない。

### 依存ソフトウェアの安全性と継続対応

アプリの開発には、外部のソフトウェア部品も使用している。2026-10-10の確認では、依存関係の監査にCritical 0件・High 46件・Moderate 12件の警告が残っている。これらは同じ問題が関連する複数の部品に数えられる場合があり、58種類の独立した問題や、58通りの個人情報漏えいが確認されたという意味ではない。件数は監査情報の更新でも変わる。

修正できる問題には対応する一方、更新によってアプリが動かなくなることや、独自修正によって別の問題を作ることも避ける。そのため、次の理由で対応を分けている。

- 対応済み: `brace-expansion`と、先に検出された`shell-quote`の問題は、現在の構成と互換性がある公式修正版へ更新した。通常の動作と、問題の再発を防ぐテストを確認している。
- 修正版待ち: `braces`・`node-forge`・`sprintf-js`には、確認時点で公式の修正版がない。現在どこで使用されるかを調べ、開発ツールへ信頼できない入力・設定・証明書を持ち込まない運用にしている。暗号処理へ独自修正を加えたり、安全確認を無効にしたりはしない。この対応はリスクを減らすもので、修正完了ではない。
- 互換性を確認してから更新: `uuid`については、警告対象の使い方が今回確認した使用経路とは異なっていた。大きなバージョン変更を強制すると、依存する開発基盤が正常に動かなくなる可能性があるため、現時点では強制更新しない。確認していない使用経路まで安全と断定しない。

今回の調査では、写真・メモなどのアプリ入力からこれらの警告対象処理へ到達する経路は確認できていない。ただし、個人情報漏えいの可能性がゼロであることや、開発ツール全体の安全性を証明したものではない。開発用サーバーは信頼できるローカル環境で使い、インターネットへ直接公開しない。`npm audit fix --force`による一括強制更新は行わない。

依存関係の更新時とアプリの公開前に、公式修正版の有無と開発基盤との互換性を再確認する。新しい入力経路・署名機能の追加や、影響範囲が変わる情報が判明した場合も判断を見直す。公開前には残るリスクを改めて評価し、必要な対策が済んでいない状態を「安全確認済み」と扱わない。

公開文書には対応状況と判断理由を記載し、実キー・認証情報・利用者データ・具体的な攻撃手順は記載しない。説明を省くこと自体を安全対策とは考えない。

### Supabaseローカル開発

Docker Desktopを起動してから、次のコマンドを使用する。

- `npm run supabase:start` — ローカルSupabaseを起動し、マイグレーションを適用する。
- `npm run supabase:status` — ローカルSupabaseの稼働状態と接続情報を確認する。
- `npm run supabase:reset` — ローカルDBを削除し、全マイグレーションを先頭から再適用する。
- `npm run supabase:stop` — ローカルSupabaseを停止する。

`npm run supabase:reset`はローカルDB内の手入力データを削除する。本番環境を対象にする`--linked`オプションは、通常のローカル開発では使用しない。

## 1. プロダクト概要

**思い出跡地**は、アプリ内カメラで撮影した写真を場所に紐付け、自分で振り返ったり、グループで共有したり、フレンドの思い出を現地で発見したりするモバイルアプリである。

自分の投稿と所属グループの投稿は、現在地に関係なく閲覧できる。フレンドの個人投稿は、未発見の間は地図にも一覧にも場所を表示しない。設定された範囲で発見するとコレクションに追加され、以後は離れた場所からも見返せる。

これは一般的な写真共有SNS、旅行記録アプリ、公開型の位置情報SNSではない。

- 写真を誰にでも見せるサービスではない
- フォロワー、いいね、公開フィードは持たない
- 自分やグループの思い出は、場所に戻らなくても振り返れる
- フレンドの未発見投稿は地図で事前に探せず、偶然の発見を楽しむ
- 思い出の共有相手は、グループとフレンド向け個人投稿で明確に分ける

### 想定する利用例

- 自分の投稿を地図から開き、初デートした日の写真をいつでも見返す
- 家族グループの写真を共有し、それぞれの場所を地図で振り返る
- 街を歩いているときにフレンドの思い出を自動で拾い、後からコレクションで見る
- 旅行中に拾った思い出を、帰宅後にコレクションから見返す

## 2. MVPで検証する価値

MVPで検証したいことは一つだけである。

> 場所と結びついた自分・グループの思い出を振り返り、フレンドの思い出を街で偶然拾う体験に、普通のアルバムにはない価値があるか。

この体験に不要な機能はMVPに入れない。

## 3. MVPの機能

### 3.1 認証

- サインアップ
- ログイン
- ログアウト

最初はメールアドレスとパスワードによる認証でよい。

### 3.2 グループ

グループは「誰と共有する思い出か」を分けるアルバムである。閲覧に現在地の条件はない。

- グループを作成できる
- 無料ユーザーは**最大5グループ**まで作成できる
- 1グループのメンバーは**最大10人**
- グループ名を設定できる
- 作成者は招待リンクまたは招待コードでメンバーを招待できる
- 招待されたユーザーは承諾または辞退できる
- メンバーは自分でグループから退出できる
- 作成者はメンバーを削除できる
- 作成者はグループを解散できる

#### 閲覧権限ルール

- 現在グループに所属しているメンバーは、場所に関係なく、そのグループの過去・現在の投稿と投稿位置を閲覧できる
- 後から参加したメンバーも、過去の投稿を閲覧できる
- グループを退出した、または削除されたメンバーは、過去・現在を含むグループの投稿と位置を閲覧できなくなる
- 再参加した場合は、再び閲覧できる
- グループを解散すると、グループ投稿は全員から閲覧できなくなる。ただし、別に作成された個人投稿は残る

グループへ招待すると、承諾したメンバーは過去の投稿・写真・正確な投稿位置も距離制限なく閲覧できる。招待承諾画面にはその旨を明記すること。

### 3.3 地図と投稿場所

- アプリ起動後のデフォルト画面はGoogle Maps
- 初期表示は自分の個人投稿のみとし、所属グループの投稿はグループごとのチェックで表示・非表示を切り替える
- フレンドの未発見の個人投稿は、地図上にマーカーも位置も表示しない
- 各投稿と撮影時の位置は個別に保存する。近い投稿を「50m以内」という固定距離で同一データへ統合しない
- 地図を縮小したときだけ近くのマーカーを表示上まとめ、拡大すると個別の投稿を表示する。異なるグループの投稿データは混ぜない
- 地図上に写真サムネイル、投稿者名、メモ本文を直接表示しない

### 3.4 フレンドと個人投稿の発見範囲

フレンド関係は相互の承認で成立する。ユーザーは申請を送り、受け取った側は承認または拒否できる。申請中・拒否後はフレンドとして扱わず、承認済みの相手を一覧で確認できる。どちらからでも解除でき、グループへの所属だけで自動的にフレンドにはならない。

- 個人投稿の発見範囲は**0m（自分専用）・半径500m・半径1km**の3択とする。初期値は0m
- 投稿者本人は範囲に関係なく自分の投稿を閲覧できる
- 0mの個人投稿はフレンドに発見・閲覧されない
- グループだけに投稿した思い出は、フレンドが近づいても発見対象にならない。グループ外のフレンドに見せたい場合は、投稿時に「自分の投稿にも載せる」を選ぶ
- 500mまたは1kmの個人投稿は、現在フレンドであるユーザーが投稿位置の範囲内で発見できる。発見後は距離に関係なくコレクションから見返せる
- フレンドになる前の移動履歴から発見を後付けしない。フレンドになった時点で現在地が範囲内なら、その時点で発見できる
- フレンドを解除したら、相手の個人投稿はコレクションに表示せず、過去に発見していても再閲覧できない
- 未発見の個人投稿の正確な位置や写真を、フレンドの端末へ事前に返さない。発見判定と権限検証はサーバー側で行う

発見範囲は「写真を開ける距離」ではない。一度発見した投稿を後から見返すことが、コレクションの目的である。半径1kmは車での移動も想定するが、OSの位置検知には遅れや停止があり、通過した全投稿の発見を保証しない。

自宅で撮影した思い出の保存は禁止しない。

### 3.5 写真投稿

- 投稿は**アプリ内カメラで撮影した写真のみ**
- 端末の写真ライブラリからアップロードする機能はMVPでは提供しない
- 撮影時の現在地を自動で保存する
- 個人投稿、または一つのグループへの投稿を選択する
- 1投稿につき写真は1枚
- 一言メモは任意
- グループ投稿では「自分の投稿にも載せる」を初期オフで表示する。オンにした場合は個人投稿の発見範囲も選択する
- 同時に作ったグループ投稿と個人投稿は、共有相手と削除時の扱いが異なる別の投稿として管理する
- 同じ撮影から作る個人投稿とグループ投稿は、一つの写真管理レコード・非公開写真ファイルを共有して参照する。写真ファイルを二重保存しない
- 「自分の投稿にも載せる」をオンにすると、グループ外のフレンドにも個人投稿の写真・メモが発見後に見えることを送信前に明示する

アプリ内カメラ限定は、過去に撮った画像を任意の場所に置くことを防ぎ、「その場で残した思い出」の価値を守るためである。

GPS偽装など、意図的なチートへの高度な対策はMVPでは行わない。通常のユーザーが他人の写真へアクセスできない権限管理を優先する。

### 3.6 発見通知とコレクション

- フレンドの個人投稿の範囲に入ると、通知を開かなくても発見済みとしてサーバーに記録し、コレクションへ自動追加する
- 複数投稿を同時に発見した場合もすべてコレクションへ追加し、通知は「思い出を3件拾いました」のようにまとめる
- 通知は発見を知らせるだけであり、通知の配信失敗や未開封によってコレクションを失わない
- コレクション一覧には投稿者と大まかな地名を表示する。投稿を開くと写真・メモを表示し、さらに「地図で見る」を選んだときに正確な投稿位置を地図上に表示する
- バックグラウンド位置情報をOSで許可したユーザーは、アプリを閉じている間も発見を試みる。許可しないユーザーは、アプリを開いている間だけ発見する
- バックグラウンドでの検知や通知はOSの制約により遅延・失敗し得る。アプリの強制終了時を含め、発見や通知の即時性は保証しない

バックグラウンド位置情報とプッシュ通知の実機検証には、Expo Goではなく専用の開発ビルドを使用する。位置情報と通知の許可は分けて扱い、通知を拒否しても発見済みの記録は残す。

### 3.7 削除

- 投稿者本人だけが自分の投稿を削除できる
- グループ投稿の削除やグループ解散は、同時に作った個人投稿を削除しない
- 個人投稿の削除はグループ投稿を削除せず、フレンドのコレクションから当該個人投稿を消す
- 削除した投稿は権限のあったユーザーからも直ちに閲覧できなくなり、その投稿の地図マーカーも消える
- グループ解散は破壊的な操作なので、グループ名の入力など強い確認を要求する

#### 写真の保持と削除順序

- 投稿削除では先にDBへ削除日時（`deleted_at`）を記録し、新たな閲覧・地図・コレクション取得の対象から外す。グループ解散はグループの解散日時（`dissolved_at`）で判定する
- 未削除の個人投稿、または未削除かつ解散していないグループの投稿のどちらかから使われている写真ファイルは保持する
- 有効な投稿から使われなくなった写真だけ、保存先からの物理削除の対象にする。削除直前に参照を再確認し、参照追加との競合で残すべき写真を消さないようにする
- 写真ファイルの削除に失敗しても投稿を閲覧可能な状態へ戻さず、削除対象を保持して再試行する
- DBの削除状態と写真ファイルの実体は別に管理する。削除済み投稿の履歴が残っていても、写真ファイルを保持する必要があるとは限らない

Issue31で投稿・写真参照・削除状態のDB基盤と、アプリからの直接アクセス拒否を実装し、Issue32で本人・現グループメンバー向けの投稿情報取得RPCを追加する。写真表示用の署名URL発行、投稿作成・削除処理、写真ファイルの物理削除、再試行の具体的な仕組み、履歴レコードの整理は後続Issueで実装する。写真管理レコードを物理削除する場合は、残る投稿の外部キー参照を先に整理する必要がある。

新しい閲覧の許可は削除時に止めるが、発行済み署名URLは有効期限まで使われる場合がある。端末保存済み画像やスクリーンショットの回収は保証しない。関連する合意事項は[仕様検討Issue #3](https://github.com/K2kitano02/omoideatochi/issues/3)と[Issue31](https://github.com/K2kitano02/omoideatochi/issues/71)にも記録する。

#### 本人・グループ向け投稿情報の取得

- テーブルをアプリから直接読み書きせず、本人一覧・グループ一覧・詳細・地図用の用途別RPCから必要な情報だけを取得する
- RPCとRLSで共通の認可判定を使い、未削除の本人個人投稿、または未解散グループの現メンバー向け投稿だけを許可する。SECURITY DEFINERのRPC内でも明示的に認可し、RLSだけに依存しない
- 自分が作ったグループ投稿でも、退出・追放後は取得できない。現メンバーは作者が退出した後も過去の投稿と作者名を閲覧できる。再参加すればグループ閲覧が再び可能になる
- 投稿詳細では、存在しない・削除済み・権限のない投稿を同じエラーで扱い、エラーの違いで存在を知らせない
- 地図用取得の初期値は本人の個人投稿のみ。選択したグループだけを追加し、投稿ID・種別・グループID・緯度経度・作成日時だけを返す。名前・メモ・写真参照は返さない
- 一覧・詳細は認可された投稿の内容と写真管理IDを返すが、写真の保存先キー・公開URL・署名URLは返さない。フレンドの個人投稿はこの取得経路の対象外
- 一覧と地図は既定50件・最大200件ずつ、作成日時とIDの降順で取得し、最後の作成日時とIDから続きを取得する。この件数は保存上限ではなく、一回の通信量の制御である
- 権限のないグループが地図の選択に含まれていたら、リクエスト全体を拒否する。退出・解散で選択が無効になった場合は、アプリ側でグループ選択を更新する必要がある

写真自体の表示・フレンド投稿の発見・画面への接続は後続Issueで実装する。認可の変更は次の取得に反映されるが、すでに端末へ送信した情報の回収や、進行中の読み取りの中断を保証するものではない。関連方針は[Issue32](https://github.com/K2kitano02/omoideatochi/issues/72)にも記録する。

#### アプリ側の投稿取得窓口

Issue33では`src/features/memories/`に、上記RPCを呼ぶ共通サービスと入力・応答の検証を追加する。画面は`getMemoryService().createReadScope()`で表示枠専用のreaderを作り、`listPersonalPosts`・`listGroupPosts`・`getPost`・`listMapPosts`を使う。成功は`ok: true`と`data`、失敗は`ok: false`と日本語の`error`を返す。

- 一つのreaderで有効なのは最新の要求だけ。一覧・詳細・地図を並列に取得する場合は、それぞれ別readerを使う
- グループや地図選択を変更するときは、先に`reader.invalidate()`し、画面側でも表示済みデータとカーソルをクリアする。遅れて届いた旧成功・旧エラーは`stale`となり、画面に表示せず捨てる
- ログアウトやユーザー変更は進行中の要求を無効化する。同一ユーザーで再ログインしてもログアウト前の応答は採用しない。通常のトークン更新だけでは無効化しない
- 画面を離れるときは`reader.dispose()`する。アプリ共通のserviceは他の画面も使うため、画面から`service.dispose()`は呼ばない。独自に生成したserviceの所有者が破棄するときだけ、サービスの監視を解除する
- 次ページは直前の取得が完了してから、成功データの`nextCursor`を渡して取得する。`nextCursor: null`なら終了。指定件数ちょうどの場合は末尾カーソルが返るが、次ページが空になる場合もある
- カーソルの日時を`Date`やミリ秒へ変換し直さず、そのまま使う。DBの小数秒精度を失うとページ境界の投稿を取りこぼす可能性がある
- 応答は固定項目だけに変換し、不正な行・取得対象違い・件数や並び順の異常があれば一覧全体を拒否する。内部エラー本文・保存先キー・余分なURL等をそのまま画面へ渡さない

この層は古い応答の採用を防ぐもので、通信の物理キャンセルや表示済みデータの自動消去は行わない。投稿内容・位置を永続キャッシュせず、閲覧権限は引き続きサーバー側で確認する。今回は画面接続・写真表示・投稿作成を実装しない。後続画面で守る条件は[Issue33](https://github.com/K2kitano02/omoideatochi/issues/73#issuecomment-6059146975)にも記録する。

## 7. セキュリティと権限の必須ルール

チート対策ではなく、通常のユーザーの写真と位置情報を守ることを優先する。

- 写真を公開URLで保存しない
- 写真を開く前に、ログイン状態、投稿の種類、現在のグループ所属・フレンド関係、発見済みかどうか、削除状態をサーバー側で確認する
- 個人投稿の発見時だけ、現在のフレンド関係と投稿位置からの距離をサーバー側で確認する。発見後の閲覧に再度の距離判定は求めない
- 条件を満たした場合だけ短時間有効な署名URLを発行する
- グループ外・退出済みのユーザーへグループの投稿を返さず、未発見またはフレンド解除後のユーザーへ個人投稿の写真・メモ・正確な位置を返さない
- グループの解散状態もサーバー側で確認する。解散済みグループの投稿は、メンバー情報が残っていても全ユーザーへ返さない
- 未発見のフレンド投稿の座標を端末へ渡して地図上だけで隠す方法は採用しない。発見と閲覧の権限はDB・サーバー側で検証する
- バックグラウンド位置情報は明示的に許可した人だけで使い、発見判定に不要な移動履歴を保存しない。許可を取り消したら背景取得を停止する
- 個人投稿は0mを初期値とし、グループ投稿を個人にも載せる選択は初期オフにする。共有相手が増える場合は送信前に説明する
- パスワードは平文保存しない
- Google Maps APIキーはiOS Bundle ID / Android Package Nameで制限する

正規に閲覧できるユーザーによるスクリーンショット保存までは防がない。守るべきなのは、権限のないユーザーへ写真や正確な位置を返さないことと、退出・フレンド解除・投稿削除後に新たな閲覧URLを取得できないことである。

## 8. MVPの最重要ユーザーフロー

### 投稿

1. ユーザーがアプリを開く
2. 地図画面からカメラを起動する
3. 写真を撮影する
4. 個人投稿か、投稿先グループを選択する
5. 個人投稿では発見範囲を0m・500m・1kmから選択する。グループ投稿を自分の投稿にも載せる場合は、明示的にチェックして個人投稿の範囲も選択する
6. 任意で一言メモを入力する
7. 現在地とともに保存する
8. 自分の投稿は地図に表示され、グループ投稿は所属メンバーが地図のチェックで表示できる

### フレンドの思い出を発見・閲覧

1. フレンドが個人投稿の設定範囲に入る
2. サーバーが現在のフレンド関係と距離を確認し、投稿を発見済みとしてコレクションへ追加する
3. 同時に複数件を拾った場合は通知を1件にまとめる。通知を開かなくても発見済みのまま残る
4. コレクション一覧から投稿を開き、写真・メモを見る
5. 必要なら「地図で見る」をタップし、正確な投稿位置を表示する
6. フレンドを解除すると、その相手の投稿はコレクションから見えなくなる

## 9. Codexへの実装指針

- MVP外の機能を追加しない。必要に見える機能でも、まず提案して確認を取る
- 画面の見栄えより、自分・グループの投稿とフレンドの発見・コレクションの一連の体験を優先する
- 5グループ上限、10人上限はフロントエンドだけでなく、DBまたはサーバー側でも必ず検証する
- 位置情報は投稿位置の保存と発見判定に必要な分だけ扱い、移動履歴の追跡・保存には利用しない
- Google Mapsはデフォルト画面とし、自分の投稿のみを初期表示する。グループの表示は選択式とし、未発見のフレンド投稿は表示しない
- 近い投稿をDBで恒久的に統合せず、地図のズームに応じて表示だけをクラスタ化する
- テストでは、0m・500m・1kmの発見境界、未発見位置の非公開、発見後の遠方閲覧、通知失敗後のコレクション保持、フレンド解除・グループ退出後のアクセス拒否、グループと個人投稿の削除の独立性を確認する

## 成功条件

MVPの成功は、次の感想が自然に出ること。

> 「友達の思い出を偶然拾った。帰ってからもコレクションで振り返れるのがいいな。」
